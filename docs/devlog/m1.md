# M1: Window and game loop

**Result:** a window opens, the loop runs with a fixed timestep of 60 updates
per second, and ticks are logged.

## Design decisions

**Fixed timestep for game logic.** Logic is updated in constant steps (1/60 s)
using an accumulator, while rendering runs at the display's pace. This keeps
physics and collisions (M6) consistent on fast and slow machines. A single
frame is clamped to 250 ms so the loop does not try to catch up forever after
a long stall.

**Timing logic lives in `ferrite-core`.** `FixedTimestep` knows nothing about
windows, so it can be tested with `advance_by(Duration)` without opening one.
There are two tests: step counting with leftover time, and long-frame clamping.

**The game implements a `Game` trait, the engine owns the loop.** A game only
implements `update` and `draw`. I used generics (`App<G: Game>`) and am still
learning to read them. The alternative is `Box<dyn Game>`.

## Observations

The "tick 60" log line did not always appear exactly once per second. The likely
cause is that I maximized and minimized the window during testing. The event
loop probably stalled, and the lost time was discarded by the 250 ms clamp,
which is intended behavior. This is a hypothesis that matches what I saw, not
something I proved.

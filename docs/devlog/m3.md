# M3: Keyboard input

**Result:** games receive an `Input` value in `update` and can ask whether a key
is held (`is_down`), was just pressed (`just_pressed`), or was just released
(`just_released`). The demo (`examples/m3_input.rs`) moves a square with WASD or
the arrow keys and toggles its color with Space.

## Design decisions

**`ferrite-input` is its own crate, and knows nothing about winit.** The engine
translates winit key codes into its own `Key` enum (in `App::window_event`);
the input crate only deals with `Key`s. That keeps the state machine testable
with plain function calls instead of synthetic OS events, and it means the game
never sees a winit type. There are six unit tests covering the edge cases
below.

**Edges are seen by exactly one update.** `Input` keeps three sets: `down`,
`pressed`, `released`. After each fixed update the engine calls
`clear_transient`, which empties `pressed` and `released` but leaves `down`
alone. This is what makes `just_pressed` fire once and only once, even when a
key is held for many ticks.

**A press and release between two updates is not lost.** Because the two edge
sets are independent of `down`, pressing and releasing Enter within one frame
leaves *both* `just_pressed` and `just_released` true, with `is_down` false.
The update sees the full edge. This is a small case, but losing a tap on a slow
frame is the kind of bug that is painful to find later.

**Physical key positions, not characters.** `Key` uses physical positions
(`KeyW`, `KeyA`, ...), so WASD sits in the same place on QWERTY, AZERTY, and
other layouts. Character-based mapping would scramble the controls.

**OS key repeat is ignored.** The event loop drops `event.repeat`, and
`handle_key` itself also ignores a "pressed" for a key already down. Belt and
braces: `just_pressed` must never fire from a repeat.

**Losing focus releases everything.** When the window unfocuses, key-release
events stop arriving, so held keys would stick forever. `WindowEvent::Focused(false)`
calls `release_all`, which moves every held key into `released`. That is the
one place where a "released" edge is synthesized rather than delivered.

## Observations

The demo normalizes the movement direction, so diagonal movement is not faster
than straight movement. That is game code, not engine code, but it is the kind
of thing every game needs, so it is worth showing in the example.

Key mapping is a plain `match` in `lib.rs`. Adding a key means adding a variant
and a match arm. Fine at this size; if `Key` grows past what one match can
comfortably hold, it could become a table, but that is not yet worth it.

## Technical notes

- `HashSet<Key>` backs each set; `Key` derives `PartialEq, Eq, Hash`.
- `clear_transient` runs *after* `game.update`, so an edge is never dropped
  before it is seen.
- The engine ignores `WindowEvent::KeyboardInput` events with `repeat == true`
  entirely.
- Versions: winit 0.30.

# M5: Entity system and game states

**Result:** a new `ferrite-ecs` crate with entities, sparse-set component
storage, and tuple queries, plus a `StateMachine` in `ferrite-core` for game
states. The demo (`examples/m5_ecs.rs`) is a small arena game: enemies spawn
and chase the player, Space squashes the nearest one for a point, and touching
an enemy goes to a Game Over screen. Menu -> Playing -> GameOver is driven by
the state machine.

## UI: text alignment

The first pass of the demo placed text with hand-tuned coordinates and it
looked bad: titles were not centered, every label used a different hardcoded
`y`, and the sizes were picked by eye. The root cause was an engine gap, not
just sloppy demo code: `draw_text` had no idea what "centered" meant, so every
game would have to redo the arithmetic.

So the fix went into the engine. `Align`, `VAlign`, and `Anchor` were added to
`ferrite-render`, and `draw_text_colored` now places a text block relative to
an anchor point. `Anchor::CENTER` centers on a point, which is what a title or
a "GAME OVER" banner wants. `measure_text` returns the world-space size so
callers can lay out panels. Thin wrappers (`draw_text`, `draw_text_anchored`)
keep the common cases short.

Two bugs surfaced while doing this, both caught by tests:

1. `measure_text` used `GLYPH_HEIGHT + 1` for every line, including the last,
   so centering a single line sat a half-pixel low. The box now hugs the
   glyphs, with the 1px gap only *between* lines.
2. The vertical anchor offsets had the wrong sign. World y is up but the font's
   y grows downward, so `VAlign::Middle`/`Bottom` must push the top edge *up*
   (`+block_h * 0.5`, `+block_h`), not down. The coordinate test failed with
   "y [2.5, -3.5] vs [2.5, -10.5]" and pinpointed it immediately.

Alignment is also now verified through the real pipeline: the headless test
`centered_text_is_horizontally_symmetric` renders the word "CENTER" to an
offscreen texture and checks the lit pixels are balanced around the middle
column, to within two pixels. It derives the block width independently of the
code under test, so it is a real check, not a tautology.

## Design decisions

**A hand-rolled ECS, no dependencies.** The design rules say no global state,
components are plain data, and everything lives in structs. A `World` is an
ordinary struct you own and pass around, which is what M6 (scene files) will
want to snapshot. Pulling in `bevy_ecs` would have been faster but would have
tied the engine's API to someone else's conventions and a large dependency
tree.

**Entities carry a generation.** An `Entity` is an index plus a generation
counter. Despawning bumps the generation, so when a slot is reused a stale
handle no longer matches it. This turns use-after-despawn from a
silent-aliasing bug into a cheap equality check. `is_alive`, `get`, and
`insert` all respect it.

**Sparse sets per component type.** Each component type gets a `SparseSet`:
dense storage for iteration, a `HashMap` from slot index to dense position for
O(1) lookup, and removal by swap-with-last. `World` keeps these in a map keyed
by `TypeId` and talks to them through a `ComponentStore` trait, so it holds
heterogeneous types while each store stays strongly typed.

**Queries are typed tuples.** `world.query::<&Pos>()` iterates one component;
`world.query::<(&Pos, &Vel)>()` yields only entities that have both. The
iterator drives from the *smallest* involved store and checks the rest, which
keeps the common "many of one, few of another" case fast. Three-element tuples
are supported too.

**Mutable access is explicit.** A combined mutable query (`&Pos` plus
`&mut Vel`) needs careful aliasing rules, so for now mutation goes through
`get_mut::<T>(entity)` or `iter_mut::<T>()`, and the demo gathers targets first
and writes afterward. This is honest about the limitation; the borrowing story
can grow when the demo game (M8) shows how much it is missed.

**State transitions are requests, not assignments.** `StateMachine::request`
queues a change; `apply` commits it at one point in the update. That means
`on_enter`-style work (like rebuilding the world) happens at a predictable
time, never in the middle of a half-updated state. The last request in a frame
wins, and applying the current state is a no-op.

**The state type is anything `Copy + PartialEq`.** `State` is a blanket impl,
so a game's own enum just works with no trait ceremony.

## Observations

The closest thing to a "gotcha" was the mutable query. Writing
`world.query::<(&Pos, &mut Vel)>()` reads well but needs a custom borrow
story, so I deferred it rather than fake it. The demo's "gather then write"
pattern is a little more code but has no surprises.

Writing tests for the demo itself (in `examples/m5_ecs.rs`) paid off twice: it
caught a wrong assumption in a test about how many enemies spawn per frame, and
it makes the game logic verifiable without a window. Combined with the headless
GPU tests from M4, most of the engine is now checked by `cargo test`.

## Technical notes

- `SparseSet::remove` uses swap-remove and must fix the moved element's sparse
  link. A test caught an early version that re-inserted the *removed* index
  instead of the moved one.
- `World::iter_mut` snapshots generations first, because it cannot hold an
  immutable borrow of the slot list and a mutable borrow of the store at once.
- `StateMachine::revision` counts applied transitions, a cheap way to detect
  "the state changed this frame".
- New crates: `ferrite-ecs`. New core module: `ferrite_core::state`. New render
  types: `Align`, `VAlign`, `Anchor`.
- Tests: 20 in `ferrite-ecs`, 11 in `ferrite-core` (6 of them for the state
  machine), 16 in `ferrite-render` plus 5 headless GPU tests, and 6 simulation
  tests in the demo example.
